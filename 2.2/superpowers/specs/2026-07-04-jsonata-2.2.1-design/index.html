    jsonata-js 2.2.1 compatibility upgrade¶

    Status (as of 2026-07-07)¶

    Phase 1 is done and merged (bbce6e7, "jsonata-js 2.2.1 Phase 1: signature engine rewrite for +/- support", #36). The submodule is bumped to v2.2.1 on main and the reference suite passes 1274/1274 — all shipped under jsonatapy 2.1.5, no version bump needed, since Phase 1 was pure bug-fix/parity work.

    Phase 2 (guardrails) is done, implemented per the 13-task docs/superpowers/plans/2026-07-07-jsonata-2.2.1-phase2-guardrails-plan.md, all tasks committed on this branch. EvaluatorOptions (timeout_ms/max_stack_depth/max_sequence_length, all Option<_>, default None = unlimited/unchanged behavior) is threaded through all three execution surfaces this port has grown beyond jsonata-js's single-engine model — the tree-walker, the "compiled expression" fast-path interpreter (eval_compiled), and the bytecode VM (vm.rs) — raising D1011 (stack depth), D1012 (timeout), and D2015 (sequence length) as applicable — these are not a 1:1 mapping to the three surfaces: D1011 is tree-walker-only (self-recursive lambdas can't compile into eval_compiled or the VM), while both D1012 and D2015 are enforced independently in all three (the VM's FilterByBytecode and eval_compiled_inner's entry checkpoint each needed their own checks, since neither shares a checkpoint with the tree-walker's evaluate_internal or with each other). Parity across all three surfaces is verified by a dedicated test suite (tests/python/test_guardrails.py, 26 cases, plus Rust-side coverage in tests/integration_test.rs and src/vm.rs's #[cfg(test)] module) that exercises both the VM-preferred path and the path forced through the tree-walker fallback.

    Two corrections were made to this document's original D2015 construct list (see the "Sequence length → D2015" section below) during implementation, verified against tests/jsonata-js/src/{jsonata,functions}.js directly rather than just this spec's summary of it: $sift is not sequence-capped upstream (sift() returns a plain filtered object, no createSequence() call — excluded, despite being named in the original list below); $lookup is sequence-capped upstream (functions.js's array-fanout branch calls createSequence() — added, despite not being in the original list below).

    One structural decision went beyond the original plan text: rather than enumerating every call site in compiled/HOF code that could bypass the D1012 timeout check, a single checkpoint was placed at the entry of eval_compiled_inner (the compiled-expression interpreter's single funnel point) plus one inside the TCO trampoline (invoke_lambda_with_tco) — these are the two execution loops that are genuinely independent of each other and of evaluate_internal's own per-node checkpoint, so no other site needed its own separate check.

    Two pre-existing bugs were found along the way. Both are now fixed, per docs/superpowers/plans/2026-07-07-parser-depth-and-u16-truncation-fixes-plan.md (branch worktree-jsonata-parser-depth-u16-fixes) — a third, previously-unknown crash surfaced during that work and was closed too: - The originally-reported crash (whole-process SIGSEGV on deeply left-nested arithmetic expressions) was root-caused to src/ast_transform.rs's post-parse AST-rebuild pass, which ran unconditionally after every parse with no recursion-depth guard — not the raw Pratt parser's own recursion for that specific shape, which stays O(1) for flat left-associative chains (the original framing above was imprecise about why, though the observed crash was real). Fixed first by adding a depth-counter + stacker::maybe_grow guard to ast_transform.rs's recursive functions (new error code U1002, no jsonata-js equivalent — a Rust-specific safety net, like U1001). Validating that fix surfaced a second, more directly reachable crash: deeply parenthesized/grouped expressions ((((...)))) recurse for real inside the parser's own parse_primary/parse_expression (src/parser.rs) and crash independently of ast_transform.rs — a genuinely different shape than the flat-chain case, since any recursive-descent parser needs real recursion to handle grouping. Both shapes are now closed by one depth guard added directly in parser.rs's parse_expression (a single shared counter bounding both loop-driven left-nesting and genuine recursive descent), reusing the U1002 code, turning either shape into a graceful coded error before ast_transform.rs ever sees the tree. ast_transform.rs's own guard remains in place as defense-in-depth (still load-bearing for mid-depth flat chains, which trip its lower effective ceiling before the parser's own limit would) rather than being removed. - Instr::MakeArray(u16) (src/compiler.rs) silently produced wrong, truncated results — not even an error — for JSONata array literals with more than 65,536 elements, because the element count is cast to u16 and overflows silently. This turned out to be one instance of a broader pattern: MakeObject, BlockEnd, and CallBuiltin's u8 arg count share the same unguarded-cast shape, plus four pool-interning u16 casts in the bytecode compiler that can overflow cumulatively across independently-compiled sibling expressions even when no single expression is oversized (e.g. many small blocks sharing one compiler's constant pool). All are now fixed the same way: the affected try_compile_* path returns None (declines to compile) instead of truncating, falling back to the tree-walker (which has no such limit and is unconditionally correct) — including a genuinely new finding along the way: CallBuiltin's arg-count guard was not already provably safe below 256 as this document's design assumed, because $merge is the one compilable builtin with an unbounded (variadic) arg count. This also unblocks a follow-up literal-array D2015 check for full upstream parity (MakeArray/ ArrayConstruct are still unguarded for length — see the "Sequence length → D2015" section below), since a length cap can now safely be layered on top of a length computation that no longer overflows.

    Per this document's Scope section below, Phase 2 is the first behavioral reason a 2.2.0 jsonatapy release would make sense — a version bump/release is a separate follow-up decision, not part of this implementation.

    Context¶

    Historical — describes the state this plan started from, before Phase 1 executed. See the Status section at the top of this document for CURRENT state: the submodule is already bumped to v2.2.1 on main, and the reference suite passes 1682/1682 against it (verified directly against the submodule's own git describe --tags and the real jsonata-js/jsonata upstream remote, not just this document, since this exact paragraph was previously left stale after Phase 1 landed and caused real confusion later — don't trust this paragraph over the Status section if they ever disagree again.)

    At plan-writing time, tests/jsonata-js (the reference test-suite submodule) was pinned at v2.1.0-3-gff36f0b (3 commits past the v2.1.0 tag). Upstream had since released v2.1.1, v2.2.0, and v2.2.1. An automated sync-jsonata.yml workflow already created a sync/jsonata-2.2.1 branch, but that branch forked from a very old point in main's history (around version 2.1.4) and predates the Null/Undefined tree-walker migration, the lambda_id fix, the compiler/VM layer's later hardening, and various CI/publishing fixes. Its only commit not already present in current main was the submodule pointer bump itself — it was not a usable starting point and was not checked out or merged. The stale sync/jsonata-2.2.0 branch had the same problem. Both sync/jsonata-2.2.1 and sync/jsonata-2.2.0 are dead branches now that Phase 1 and Phase 2 have both landed via separate PRs (#36, #56) — delete them.

    Diffing jsonata-js from our current commit (ff36f0b) to v2.2.1 shows real upstream changes: a new resource-guardrails feature (timeout/stack/sequence options, new errors D1011/D1012/ D1013), several prototype-pollution hardening changes specific to JS's shared-prototype-chain object model, a wildcard-vs-function-object fix, a parser AST-node-sharing bug fix for ??/?:, $formatNumber/ISO8601/$toMillis bug fixes, and a signature-matching refinement — plus 17 new reference-suite test cases.

    Locally bumping the submodule to v2.2.1 and running the full reference suite showed 1268/1274 already passing. The only 6 failures are all in function-signatures (case035–case040), and all trace to one root cause: our signature-literal tokenizer (src/parser.rs::parse_signature) rejects the + (one-or-more repeat) modifier outright, and src/signature.rs's hand-rolled matcher has no concept of repeating params at all. Every other upstream behavioral change (wildcards, formatNumber, ISO8601, $lookup) already behaves correctly in this Rust port and is not exercised as a regression by the new test cases.

    Scope¶

    This project has two phases, each its own branch/PR/review cycle. Phase 2 starts only after Phase 1 merges.

    • Phase 1 — reference-suite parity. Bump the submodule to v2.2.1 on a fresh branch off current main (not the stale sync branches) and rewrite the signature-matching engine to support +. Target: 1274/1274 reference-suite pass.
    • Phase 2 — guardrails feature. Port jsonata-js's new resource-limit options (timeout, stack, sequence) to both the Rust (jsonata-core) and Python (jsonatapy) public APIs, even though no reference-suite case exercises them, for API parity with upstream 2.2.1.

    Explicitly out of scope: anything from jsonata-js versions beyond 2.2.1, and non-behavioral upstream changes (Go/C++ reference implementations, CI/docs-only commits).

    Phase 1: signature engine rewrite¶

    Parser fix (src/parser.rs::parse_signature)¶

    Add a Token::Plus => { signature.push('+'); self.advance()?; } arm alongside the existing Minus/Question/QuestionColon handling in the signature-literal token collector, so + survives into the collected signature string instead of producing ParserError::UnexpectedToken("Unexpected token in signature: Plus").

    src/signature.rs rewrite¶

    Mirror signature.js's parseSignature algorithm (regex-based) instead of the current recursive-descent hand-rolled matcher:

    • Each param gets a regex: String fragment built from its type char(s), using the same char-class table as JS: simple types → one-char class (e.g. n → [nm], where m means "missing/undefined" so optional-detection still works via the regex engine), a → [asnblfom] (anything coerces to a singleton array), f → f, x/j → wider classes, union types like (ns) → [nsm], etc.
    • ? appends ? to the current param's regex fragment (0-or-1 quantifier). + appends + (1-or-more quantifier). - sets a context/contextRegex flag on the previous param (fall back to the $ context value if the arg is omitted) and also makes that param's regex ?.
    • Build ^(<p1>)(<p2>)...$ and compile with the regex crate (already a dependency) once per Signature::parse call — this happens once per lambda/function definition, not per call, so it is not a hot-path regex compile.
    • At call time: build a type-symbol string from the actual supplied argument types (one char per arg — f for lambdas/builtins, etc.), match the compiled regex against it, and for each captured group walk its matched chars back to positional args, pushing one validated arg per matched char and applying array-wrapping/type-checking/context-substitution exactly where JS does (the param.type === 'a' and 'm'-means-missing branches identified in the upstream diff).
    • ParamType/Parameter stay as typed enums/structs (not stringly-typed like JS) — only the matching strategy changes to regex-driven. ParamType::matches() and coercion logic are reused, not rewritten.

    Verification¶

    • The 6 currently-failing function-signatures cases (035–040) pass.
    • Full reference suite: 1274/1274 (uv run pytest tests/python/test_reference_suite.py).
    • cargo test stays green (existing signature-related unit tests — union types, array subtypes, function subtypes, context - fallback — all route through the new engine and must keep passing).
    • New Rust unit tests in signature.rs's #[cfg(test)] module covering +/-/? combinations beyond the 6 reference cases (e.g. multiple repeats, repeat-then-optional).

    Phase 2: guardrails feature¶

    Rust API (jsonata-core)¶

    #[derive(Default, Clone)]
pub struct EvaluatorOptions {
    pub timeout_ms: Option<u64>,
    pub max_stack_depth: Option<usize>,
    pub max_sequence_length: Option<usize>,
}

    Exposed via Evaluator::with_options(..., EvaluatorOptions) (exact constructor shape to be finalized during implementation planning, to fit both the tree-walker's existing constructor and however the compiled-VM path threads options through). All fields default None = unlimited, preserving current behavior exactly when unspecified. Evaluator::new() remains unchanged for existing callers.

    Stack depth → D1011¶

    Extend the existing recursion_depth/max_recursion_depth mechanism in evaluator.rs (currently a hardcoded internal safety net that throws U1001 on overflow, paired with stacker::maybe_grow for actual native-stack growth) rather than replacing it. When max_stack_depth is set and lower than the hardcoded ceiling, exceeding it throws D1011 instead. The hardcoded U1001 ceiling remains as an always-on backstop against actual native stack exhaustion regardless of user options — this is a Rust-specific concern (see GitHub issue

    34, referenced in evaluator.rs) that jsonata-js does not need an equivalent for, since it has¶

    no separate native-stack-overflow failure mode.

    Timeout → D1012¶

    New. Capture a start Instant when evaluation begins; check elapsed time against timeout_ms at the same checkpoint where recursion depth is already checked per node (evaluate_internal), so it piggybacks on an existing hot-path check rather than introducing a new timer thread.

    Sequence length → D2015¶

    New plumbing — unlike depth/timeout there is no existing hook for this. jsonata-js applies this cap to query-result sequences (map/filter/group/wildcard/descendants/append/spread/keys/each/ sift/range) and to flat/non-nested literal array construction ([1,2,3]): upstream's array literal evaluation (evaluateUnary's [ case, tests/jsonata-js/src/jsonata.js:544) routes each non-nested element through fn.append, which itself calls the createSequence-based cap (tests/jsonata-js/src/functions.js:1727) — confirmed empirically against live jsonata-js: [1,2,3,4,5] with sequence: 2 raises D2015 upstream. Nested-array literals (e.g. [[1,2],[3,4]]) escape the cap in upstream, since each nested sub-array is a single element passed to append, not fanned out.

    This Rust port currently caps only the query-result sites, not literal array construction — Instr::MakeArray/CompiledExpr::ArrayConstruct are unguarded, a deliberate, temporary divergence from upstream. This was originally entangled with the (now-fixed, per the Status section's bug list) MakeArray(u16) truncation bug — a length check couldn't safely be layered on top of a length computation that itself overflowed silently for arrays over 65,536 elements. That truncation bug is fixed now, which unblocks adding this literal-array D2015 cap safely — but the cap itself has not been added yet; it remains a known gap and a candidate for its own follow-up. The Rust port's nested-array-literals-escape-the-cap behavior already matches upstream correctly; only the flat-literal case is a known gap. The implementation plan enumerates every query-result call site that IS guarded in both the tree-walker (evaluator.rs) and the bytecode VM (vm.rs) — since compiled expressions run through the VM by default, the same cap must be enforced at the equivalent instructions there (map/filter opcodes, etc.) or the VM path would silently bypass the guardrail for any expression that happens to compile.

    D2014's message (range-operator size cap) already says "10,000,000" matching upstream's 2.2.1 wording bump from 1e6 — no action needed there.

    Python API (jsonatapy)¶

    Keyword arguments on evaluate(), compile(), and JsonataExpression.evaluate():

    def evaluate(expr: str, data: Any, *, timeout: int | None = None,
              max_stack_depth: int | None = None,
              max_sequence_length: int | None = None) -> Any: ...

expr = jsonatapy.compile("...", timeout=5000)
result = expr.evaluate(data)

    These convert to EvaluatorOptions at the PyO3 boundary in lib.rs.

    Verification¶

    No reference-suite case exercises guardrails, so new tests are needed under tests/python/ (e.g. test_guardrails.py): - timeout triggers on a slow/pathological expression. - max_stack_depth triggers on deep recursion, throwing D1011 (not U1001) when the user limit is the one that trips. - max_sequence_length triggers on a large map/filter/range result. - Parity test: identical guardrail-triggering behavior whether the expression takes the VM-compiled path or is forced through the tree-walker fallback — mirroring how the Null/Undefined migration was verified against both paths.

    JS-specific changes that are N/A¶

    The prototype-pollution hardening in upstream (Object.create(null), hasOwnProperty.call guards, D1013's rejection of _jsonata_lambda/_jsonata_function group-by keys) exists because JS objects share a prototype chain that JSON-sourced keys can collide with. Our IndexMap<String, JValue> has no prototype chain, so $lookup, wildcards, and group-by already cannot exhibit this class of bug. Phase 1 includes a quick confirmation test (e.g. $lookup({"toString": 1}, "toString") behaves correctly) rather than porting defensive code that solves a problem this implementation doesn't have.

    Repo hygiene¶

    Delete the stale sync/jsonata-2.2.1 and sync/jsonata-2.2.0 branches once Phase 1's real branch supersedes them, so the automated sync-jsonata.yml workflow doesn't get confused finding old branches for versions already surpassed.
