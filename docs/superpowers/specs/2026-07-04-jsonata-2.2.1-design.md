# jsonata-js 2.2.1 compatibility upgrade

## Status (as of 2026-07-07)

**Phase 1 is done and merged** (`bbce6e7`, "jsonata-js 2.2.1 Phase 1: signature engine rewrite for
+/- support", #36). The submodule is bumped to `v2.2.1` on `main` and the reference suite passes
1274/1274 — all shipped under jsonatapy `2.1.5`, no version bump needed, since Phase 1 was pure
bug-fix/parity work.

**Phase 2 (guardrails) is done**, implemented per the 13-task
`docs/superpowers/plans/2026-07-07-jsonata-2.2.1-phase2-guardrails-plan.md`, all tasks committed
on this branch. `EvaluatorOptions` (`timeout_ms`/`max_stack_depth`/`max_sequence_length`, all
`Option<_>`, default `None` = unlimited/unchanged behavior) is threaded through all three
execution surfaces this port has grown beyond jsonata-js's single-engine model — the tree-walker,
the "compiled expression" fast-path interpreter (`eval_compiled`), and the bytecode VM (`vm.rs`) —
raising `D1011` (stack depth), `D1012` (timeout), and `D2015` (sequence length) respectively.
Parity across all three surfaces is verified by a dedicated test suite
(`tests/python/test_guardrails.py`, 26 cases, plus Rust-side coverage in
`tests/integration_test.rs` and `src/vm.rs`'s `#[cfg(test)]` module) that exercises both the
VM-preferred path and the path forced through the tree-walker fallback.

Two corrections were made to this document's original D2015 construct list (see the "Sequence
length → D2015" section below) during implementation, verified against
`tests/jsonata-js/src/{jsonata,functions}.js` directly rather than just this spec's summary of it:
`$sift` is **not** sequence-capped upstream (`sift()` returns a plain filtered object, no
`createSequence()` call — excluded, despite being named in the original list below); `$lookup`
**is** sequence-capped upstream (`functions.js`'s array-fanout branch calls `createSequence()` —
added, despite not being in the original list below).

One structural decision went beyond the original plan text: rather than enumerating every call
site in compiled/HOF code that could bypass the `D1012` timeout check, a single checkpoint was
placed at the entry of `eval_compiled_inner` (the compiled-expression interpreter's single funnel
point) plus one inside the TCO trampoline (`invoke_lambda_with_tco`) — these are the two execution
loops that are genuinely independent of each other and of `evaluate_internal`'s own per-node
checkpoint, so no other site needed its own separate check.

Two pre-existing bugs were found along the way. Both are **out of scope for this plan and were
NOT fixed** — they're recorded here for future work, not claimed as resolved:
- The parser has no recursion-depth guard and can crash the whole process (SIGSEGV) on deeply
  left-nested arithmetic expressions (roughly 4000+ terms) — independent of, and prior to, the
  evaluator's own `D1011`/`U1001` guards, which never get a chance to run since the crash happens
  during parsing, before evaluation starts.
- `Instr::MakeArray(u16)` (`src/compiler.rs`) silently produces **wrong, truncated** results — not
  even an error — for JSONata array literals with more than 65,536 elements, because the element
  count is cast to `u16` and overflows silently. This is more severe than the parser crash (silent
  data corruption vs. a loud failure) and should be prioritized in any follow-up.

Per this document's Scope section below, Phase 2 is the first behavioral reason a `2.2.0`
jsonatapy release would make sense — a version bump/release is a separate follow-up decision, not
part of this implementation.

## Context

`tests/jsonata-js` (the reference test-suite submodule) is currently pinned at `v2.1.0-3-gff36f0b`
(3 commits past the `v2.1.0` tag). Upstream has since released `v2.1.1`, `v2.2.0`, and `v2.2.1`.
An automated `sync-jsonata.yml` workflow already created a `sync/jsonata-2.2.1` branch, but that
branch forked from a very old point in `main`'s history (around version 2.1.4) and predates the
Null/Undefined tree-walker migration, the `lambda_id` fix, the compiler/VM layer's later
hardening, and various CI/publishing fixes. Its only commit not already present in current `main`
is the submodule pointer bump itself — it is not a usable starting point and should not be checked
out or merged. The stale `sync/jsonata-2.2.0` branch has the same problem.

Diffing `jsonata-js` from our current commit (`ff36f0b`) to `v2.2.1` shows real upstream changes:
a new resource-guardrails feature (`timeout`/`stack`/`sequence` options, new errors D1011/D1012/
D1013), several prototype-pollution hardening changes specific to JS's shared-prototype-chain
object model, a wildcard-vs-function-object fix, a parser AST-node-sharing bug fix for `??`/`?:`,
`$formatNumber`/ISO8601/`$toMillis` bug fixes, and a signature-matching refinement — plus 17 new
reference-suite test cases.

Locally bumping the submodule to `v2.2.1` and running the full reference suite showed **1268/1274
already passing**. The only 6 failures are all in `function-signatures` (case035–case040), and all
trace to one root cause: our signature-literal tokenizer
(`src/parser.rs::parse_signature`) rejects the `+` (one-or-more repeat) modifier outright, and
`src/signature.rs`'s hand-rolled matcher has no concept of repeating params at all. Every other
upstream behavioral change (wildcards, formatNumber, ISO8601, `$lookup`) already behaves correctly
in this Rust port and is not exercised as a regression by the new test cases.

## Scope

This project has two phases, each its own branch/PR/review cycle. Phase 2 starts only after
Phase 1 merges.

- **Phase 1 — reference-suite parity.** Bump the submodule to `v2.2.1` on a fresh branch off
  current `main` (not the stale sync branches) and rewrite the signature-matching engine to
  support `+`. Target: 1274/1274 reference-suite pass.
- **Phase 2 — guardrails feature.** Port jsonata-js's new resource-limit options (`timeout`,
  `stack`, `sequence`) to both the Rust (`jsonata-core`) and Python (`jsonatapy`) public APIs, even
  though no reference-suite case exercises them, for API parity with upstream 2.2.1.

Explicitly out of scope: anything from jsonata-js versions beyond 2.2.1, and non-behavioral
upstream changes (Go/C++ reference implementations, CI/docs-only commits).

## Phase 1: signature engine rewrite

### Parser fix (`src/parser.rs::parse_signature`)

Add a `Token::Plus => { signature.push('+'); self.advance()?; }` arm alongside the existing
`Minus`/`Question`/`QuestionColon` handling in the signature-literal token collector, so `+`
survives into the collected signature string instead of producing
`ParserError::UnexpectedToken("Unexpected token in signature: Plus")`.

### `src/signature.rs` rewrite

Mirror `signature.js`'s `parseSignature` algorithm (regex-based) instead of the current
recursive-descent hand-rolled matcher:

- Each param gets a `regex: String` fragment built from its type char(s), using the same
  char-class table as JS: simple types → one-char class (e.g. `n` → `[nm]`, where `m` means
  "missing/undefined" so optional-detection still works via the regex engine), `a` → `[asnblfom]`
  (anything coerces to a singleton array), `f` → `f`, `x`/`j` → wider classes, union types like
  `(ns)` → `[nsm]`, etc.
- `?` appends `?` to the current param's regex fragment (0-or-1 quantifier). `+` appends `+`
  (1-or-more quantifier). `-` sets a `context`/`contextRegex` flag on the previous param (fall
  back to the `$` context value if the arg is omitted) and also makes that param's regex `?`.
- Build `^(<p1>)(<p2>)...$` and compile with the `regex` crate (already a dependency) once per
  `Signature::parse` call — this happens once per lambda/function *definition*, not per call, so
  it is not a hot-path regex compile.
- At call time: build a type-symbol string from the actual supplied argument types (one char per
  arg — `f` for lambdas/builtins, etc.), match the compiled regex against it, and for each
  captured group walk its matched chars back to positional args, pushing one validated arg per
  matched char and applying array-wrapping/type-checking/context-substitution exactly where JS
  does (the `param.type === 'a'` and `'m'`-means-missing branches identified in the upstream diff).
- `ParamType`/`Parameter` stay as typed enums/structs (not stringly-typed like JS) — only the
  *matching strategy* changes to regex-driven. `ParamType::matches()` and coercion logic are
  reused, not rewritten.

### Verification

- The 6 currently-failing `function-signatures` cases (035–040) pass.
- Full reference suite: 1274/1274 (`uv run pytest tests/python/test_reference_suite.py`).
- `cargo test` stays green (existing signature-related unit tests — union types, array
  subtypes, function subtypes, context `-` fallback — all route through the new engine and must
  keep passing).
- New Rust unit tests in `signature.rs`'s `#[cfg(test)]` module covering `+`/`-`/`?` combinations
  beyond the 6 reference cases (e.g. multiple repeats, repeat-then-optional).

## Phase 2: guardrails feature

### Rust API (`jsonata-core`)

```rust
#[derive(Default, Clone)]
pub struct EvaluatorOptions {
    pub timeout_ms: Option<u64>,
    pub max_stack_depth: Option<usize>,
    pub max_sequence_length: Option<usize>,
}
```

Exposed via `Evaluator::with_options(..., EvaluatorOptions)` (exact constructor shape to be
finalized during implementation planning, to fit both the tree-walker's existing constructor and
however the compiled-VM path threads options through). All fields default `None` = unlimited,
preserving current behavior exactly when unspecified. `Evaluator::new()` remains unchanged for
existing callers.

### Stack depth → D1011

Extend the *existing* `recursion_depth`/`max_recursion_depth` mechanism in `evaluator.rs`
(currently a hardcoded internal safety net that throws `U1001` on overflow, paired with
`stacker::maybe_grow` for actual native-stack growth) rather than replacing it. When
`max_stack_depth` is set and lower than the hardcoded ceiling, exceeding it throws `D1011`
instead. The hardcoded `U1001` ceiling remains as an always-on backstop against actual native
stack exhaustion regardless of user options — this is a Rust-specific concern (see GitHub issue
#34, referenced in `evaluator.rs`) that jsonata-js does not need an equivalent for, since it has
no separate native-stack-overflow failure mode.

### Timeout → D1012

New. Capture a start `Instant` when evaluation begins; check elapsed time against `timeout_ms` at
the same checkpoint where recursion depth is already checked per node (`evaluate_internal`), so
it piggybacks on an existing hot-path check rather than introducing a new timer thread.

### Sequence length → D2015

New plumbing — unlike depth/timeout there is no existing hook for this. jsonata-js applies this
cap only to *query-result* sequences (map/filter/group/wildcard/descendants/append/spread/keys/
each/sift/range), not literal array construction (`[1,2,3]`). The Rust port needs equivalent
scoping: enforce the cap at the analogous result-construction sites in `evaluator.rs`, **and**
since compiled expressions run through the bytecode VM by default, the same cap must be enforced
at the equivalent instructions in `vm.rs` (`MakeArray`, map/filter opcodes, etc.) — otherwise the
VM path would silently bypass the guardrail for any expression that happens to compile. This is
the largest, most invasive piece of Phase 2; the implementation plan must enumerate every such
call site in both engines.

`D2014`'s message (range-operator size cap) already says "10,000,000" matching upstream's 2.2.1
wording bump from 1e6 — no action needed there.

### Python API (`jsonatapy`)

Keyword arguments on `evaluate()`, `compile()`, and `JsonataExpression.evaluate()`:

```python
def evaluate(expr: str, data: Any, *, timeout: int | None = None,
              max_stack_depth: int | None = None,
              max_sequence_length: int | None = None) -> Any: ...

expr = jsonatapy.compile("...", timeout=5000)
result = expr.evaluate(data)
```

These convert to `EvaluatorOptions` at the PyO3 boundary in `lib.rs`.

### Verification

No reference-suite case exercises guardrails, so new tests are needed under
`tests/python/` (e.g. `test_guardrails.py`):
- `timeout` triggers on a slow/pathological expression.
- `max_stack_depth` triggers on deep recursion, throwing D1011 (not U1001) when the user limit is
  the one that trips.
- `max_sequence_length` triggers on a large map/filter/range result.
- Parity test: identical guardrail-triggering behavior whether the expression takes the
  VM-compiled path or is forced through the tree-walker fallback — mirroring how the
  Null/Undefined migration was verified against both paths.

## JS-specific changes that are N/A

The prototype-pollution hardening in upstream (`Object.create(null)`, `hasOwnProperty.call`
guards, D1013's rejection of `_jsonata_lambda`/`_jsonata_function` group-by keys) exists because
JS objects share a prototype chain that JSON-sourced keys can collide with. Our
`IndexMap<String, JValue>` has no prototype chain, so `$lookup`, wildcards, and group-by already
cannot exhibit this class of bug. Phase 1 includes a quick confirmation test (e.g.
`$lookup({"toString": 1}, "toString")` behaves correctly) rather than porting defensive code that
solves a problem this implementation doesn't have.
